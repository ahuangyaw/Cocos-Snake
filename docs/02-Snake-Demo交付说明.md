## 二、我为什么选贪吃蛇

不是为了简单，而是因为**它是最能暴露工程能力的最小题目**：

| 贪吃蛇要求的能力 | 通用性 |
| --- | --- |
| 格子坐标 ↔ 像素坐标换算 | 所有 2D 游戏 |
| **固定时间步长**（逻辑频率 ≠ 渲染帧率） | 所有游戏的地基 |
| **插值渲染**（低逻辑频率 + 高帧率 = 顺滑） | 所有游戏的手感来源 |
| **输入缓冲队列** | 所有有操作感的游戏 |
| **确定性**（同种子 + 同输入 = 同结果） | 回放 / 录像 / 联机同步 / bug 复现 |
| 状态机（进行中 / 暂停 / 结束） | 所有游戏 |
| 程序化渲染（不依赖美术） | 快速原型 / 小游戏 |
| 缓动、震屏、粒子、"打击感" | 决定"爽不爽" |

**这 8 项能力，换成任何玩法都成立。** 我做的不是一个贪吃蛇，是一套可以复用的骨架。

## 三、架构：三层严格分离

```
assets/scripts/snake/
├── SnakeCore.ts     ← 纯逻辑核心（12KB，不 import 任何 cc）
├── SnakeView.ts     ← 渲染 + 手感层（Graphics 程序化绘制）
└── SnakeGame.ts     ← 输入层 + 总装配
```

### 1. `SnakeCore` —— 纯逻辑，零引擎依赖

**这是整个交付里最重要的设计决定。**

它不 `import` 任何 Cocos API，所以：

- ✅ **可以在 Node 里跑单元测试**（下面第四节，51 条断言全绿）
- ✅ **可移植**：换渲染层（贴图 / Spine / 抖音自绘）不用改一行逻辑
- ✅ **确定性**：内置 xorshift32 伪随机 + 固定步长，相同种子和输入必得相同结果

坐标用格子 `(x, y)`，不用像素——**逻辑层永远不该知道像素是什么**。

### 2. `SnakeView` —— 只管画，从不改逻辑

- 每帧**只读** `SnakeCore` 的状态
- **插值渲染**：逻辑每 0.16 秒走一格，但渲染跑满 60/120 帧，在两次逻辑步之间做线性插值 → 格子游戏也有连续运动
- **静态/动态分层**：棋盘背景是独立 `Graphics`，只在尺寸变化时画一次；每帧只重画蛇、食物、粒子
- 所有圆角矩形**攒成一条路径再一次 `fill()`** —— `Graphics` 每次 `fill` 都要重建网格，这是性能关键

### 3. `SnakeGame` —— 输入与装配

- 键盘 + 触屏滑动
- 输入不直接改方向，而是写进 `SnakeCore.inputQueue`，由逻辑层按规则消费

## 四、我做的验证（这份 Demo 我敢担保逻辑正确）

### 逻辑核心：51 条单元测试，全部通过

```
node tools/test_snake_core.js temp/core-js/SnakeCore.js
```

覆盖：初始状态 / 前进 / 吃食物 / **四个方向撞墙** / 撞自己 / **尾巴让位** /
**输入缓冲三条规则** / 反向判定基准 / 确定性 / 3000 步压力测试 / 极端尺寸 / **食物可达性**

三个我认为最值钱的测试：

**① 尾巴让位** —— 头进入「本步会腾空的尾巴格」不应判死。
少了这个判断，贴着自己转弯时会**莫名其妙暴毙**（新手必踩，且极难查）。

**② 反向判定的基准必须是队列尾，而不是当前方向**

```ts
// 当前向右；玩家先按「上」，再按「下」
const base = this.inputQueue.length > 0
    ? this.inputQueue[this.inputQueue.length - 1]   // ← 必须是队列尾
    : this.dir;
```
若错误地拿「当前方向(右)」判断，向下是合法的会被接受 → 蛇先向上再立刻向下 → **自己撞死自己**。

**③ 食物可达性** —— 用洪水填充（BFS）确保食物不生成在被蛇身围出的死区里。
少了它，玩家会看到食物却永远吃不到。

### 类型检查：对着引擎完整类型声明，零错误

```powershell
tsc -p temp/tsconfig.ai-check.json   # include 全部 assets/scripts/**/*.ts
# 退出码 0
```

### 一个诚实的踩坑记录

第一次跑测试有 2 条失败。我一看就知道**是测试错了不是引擎错了**：
测试用 `g.snake = [...]` 直接改蛇身，但没同步内部的 `_occupied` 占用位图，
导致撞自己检测读到空棋盘。

修法不是「改测试绕过」，而是**给核心加上 `rebuildOccupancy()` + `validate()`**，
把「派生数据必须与源数据一致」这条不变量显式化：

```ts
/** 调试/测试用：校验内部状态是否自洽 */
public validate(): string[] { ... }   // 占用位图 vs 蛇身，逐格比对
```

> 这体现一条工程原则：**当测试和实现冲突时，先怀疑自己对不变量的表达是否清晰，
> 而不是急着改断言让它变绿。**

## 五、手感细节（"爽不爽"就靠这些）

| 细节 | 作用 |
| --- | --- |
| **固定步长 + 插值** | 顺滑，且速度可精确调 |
| 速度随进食**渐进加快**（0.16s → 0.062s） | 越玩越紧张 |
| 分数**越吃越值钱**（+10 起，每次多吃 +2，上限 +40） | 正反馈 |
| **输入缓冲（最多 2 个）** | 快速连按不丢，且**不制造操作延迟** |
| 吃食物：**粒子爆散 + 轻微震屏 + 头部涨大** | 打击感 |
| 死亡：**红色闪屏 + 强震屏 + 粒子** | 失败反馈 |
| 尾部随插值**收缩**而非突然消失 | 视觉上像"抽走" |
| 蛇身**头亮尾暗**渐变 | 一眼看出方向与长度 |
| 眼睛**朝运动方向偏移** | 有生命感 |
| 食物**脉动 + 光晕** | 引导视线 |
| **屏幕震动用平方衰减** | 尾巴自然停下，不是硬切 |
| `dt > 0.1` 夹住 | 切后台回来不会一帧冲出去撞墙（移动端必做） |

## 七、下一步：为抖音小游戏铺路

这个 Demo 已经具备上小游戏的基础，但真机适配还需要：

| 待办 | 说明 |
| --- | --- |
| **屏幕适配策略** | 横屏 960×640 要改成竖屏；用 `view.setDesignResolutionSize` + `FitHeight` |
| **点击/滑动的坐标换算** | 真机 DPR 与设计分辨率不同，要用 `UITransform.convertToNodeSpaceAR` |
| **包体控制** | 抖音小游戏对首包有大小限制，程序化绘制恰好是优势（无贴图） |
| **性能预算** | 目标 60fps；`Graphics` 每帧重建网格在低端机上要实测 |
| **平台 SDK** | `tt.` 命名空间的 API 封装层、录屏分享、排行榜 |
| **音频** | 吃食物/死亡音效（WebAudio 在部分小游戏平台有坑） |
| **数据持久化** | 最高分存 `tt.setStorageSync` |
| **分包/远程资源** | 超过首包限制时的策略 |

**你下一步想先做哪个？** 我的建议顺序：① 屏幕适配（竖屏）→ ② 音效 + 最高分持久化
→ ③ 平台 SDK 封装层 → ④ 性能实测。
